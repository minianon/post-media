This week I shipped a lot into AnonVault, my personal workspace app. The most useful change was a bug fix.

Shipped this week:

- Fixed subtask ticks not saving. Tasks are now local-first: a change that fails to reach Supabase stays on the device in a pending queue and is retried on the next load, instead of being overwritten by the server copy.
- Live sync across devices. The app subscribes to Supabase Realtime and re-syncs only the table that changed, debounced. A timer catches anything missed.
- An hour-by-hour Week and Day calendar with meeting reminders, plus an installable app that opens offline.
- Every section is now lazy-loaded, so first load dropped from about 240 KB to about 146 KB gzipped.

What broke: subtask ticks were not saving. A background reload could replace a local change with the older server copy. The fix was to run task operations one at a time and keep unsent changes on the device until they upload.

Lesson: if the screen shows a state the database never received, the app is lying to you. Make the write durable first, then sync.

1/5 Page 1 of your feed API is instant. Page 500 crawls.

Same query, same table. The only thing that changed is the page number.

The culprit is usually OFFSET.

2/5 OFFSET 10000 LIMIT 20 doesn't jump to row 10,000.

The database reads past 10,000 rows, throws them away, then returns 20. The deeper the page, the more wasted work.

3/5 Keyset pagination fixes it: remember the last row you showed.

Next page: WHERE id < :last_id ORDER BY id DESC LIMIT 20

With an index on id, the database seeks straight there.

4/5 The trade-offs:

- no "jump to page 87"
- you need a stable, unique sort key (use created_at + id as a tie-breaker)

Bonus: rows inserted mid-scroll don't shift your pages.

5/5 Rule of thumb: small admin table with numbered pages, OFFSET is fine. Infinite feed or big table, go keyset.
