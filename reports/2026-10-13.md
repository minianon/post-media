Pattern of the week: Sliding window.

If a problem asks for the longest or shortest contiguous chunk of an array or string, stop and think window.

How to spot it:
- Contiguous subarray or substring
- Longest, shortest, max or min
- A rule to keep valid, like "no repeats" or "sum at least K"

The template is always the same four steps:
1. Expand the right end
2. Update the counts
3. Shrink from the left while the window is invalid
4. Record the best answer

Each element enters and leaves the window once, so a nested-loop O(n^2) becomes O(n).

Three problems to practise, in this order:
- Longest Substring Without Repeating Characters
- Minimum Size Subarray Sum
- Longest Repeating Character Replacement

Solve the first one using only the template above, then notice how little changes in the other two.

How I built HireLens, an AI resume screener, and the one rule I'd keep in every LLM app.

The problem: a recruiter gets a pile of resumes for one role. Reading each one properly takes hours, and by resume 30 everyone is skimming.

So HireLens takes a job description plus up to 10 resumes (PDF, DOCX or TXT) and returns a ranked list. Each candidate gets a 0-100 match score, 2-3 strengths, 2-3 gaps and a short recruiter note.

The architecture is deliberately simple:
- Next.js 14 with one API route, POST /api/screen
- Clerk for auth
- pdf-parse and mammoth to pull text out of the files
- Groq (Llama 3.3 70B) to evaluate each resume against the JD
- Cloudinary for the original files, Supabase PostgreSQL for sessions and candidates

The interesting part is not the model call. It's everything around it.

Three decisions I'm glad I made:

1. Never trust the model's label. The prompt asks for strict JSON, but the code clamps the score to 0-100 and derives "Strong / Moderate / Not Fit" from the number itself. The model suggests, the code decides.

2. One bad resume must not sink the batch. Resumes are analysed in parallel with Promise.allSettled, so a corrupt file fails alone and the rest still get ranked.

3. Non-critical steps stay non-critical. If the Cloudinary upload fails, the screening carries on.

The lesson: treat LLM output like user input. Parse it, validate it, cap it, and never let it decide anything your code can decide.

1/4 One slow service can take down your whole app. The circuit breaker pattern stops that. Explained in 4 tweets 🧵

2/4 Remote calls can fail or hang. If many callers keep waiting on a dead service, you run out of resources and the failure cascades.

A circuit breaker wraps the call and watches for failures.

3/4 Three states:

Closed: requests pass through normally.
Open: too many failures, so calls fail instantly without touching the service.
Half-open: after a timeout, a few trial requests go through. Success closes it, failure re-opens it.

4/4 Fail fast beats waiting on a timeout, and the struggling service gets room to recover.
