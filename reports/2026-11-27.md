1/5 Your API is public. One script starts sending thousands of requests a second.

Without a limit, it slows down every other user. Rate limiting decides who gets through.

2/5 It sits in front of your API servers, as a gateway or middleware.

Every request is checked against a counter first. Under the limit: it goes through. Over it: the client gets 429 Too Many Requests.

3/5 Token bucket: a bucket holds N tokens and refills at a steady rate. Each request spends one token.

Empty bucket means rejected. It allows short bursts but keeps the average steady.

4/5 Fixed window counter: count requests per user per minute. Simple, but it has a boundary problem.

A user can send the full limit at the end of one minute and again at the start of the next. Sliding windows smooth that out.

5/5 With many servers, the counters must be shared (an in-memory store like Redis is the usual choice). Otherwise each server enforces its own limit.

More notes: https://github.com/minianon/System-Design
