Process vs thread: the one interview question that trips up more freshers than it should.

Here is the version I would give in an interview.

A process is a program in execution. It gets its own memory space.

A thread is a lightweight path of execution inside a process. It has its own stack, program counter and registers, but it shares the process's memory with the other threads.

That one difference explains everything else:

- Creating and ending a thread is cheaper than a process
- Threads share data easily, so they also share bugs (race conditions)
- A crash in one process usually does not take down another, but a bad thread can take down its whole process
- Processes need explicit ways to talk to each other, threads just read the same memory

The follow-up interviewers love: "Then why not use threads for everything?"

Because shared memory means you now need locks, and locks mean deadlocks and subtle bugs. Isolation is a feature.

5 debugging habits that save hours:

1. Reproduce it before you touch any code
2. Read the actual error message, fully
3. Change one thing at a time
4. Run git diff before blaming the framework
5. Explain the bug out loud, line by line

Most bugs show up at step 5.

1/4 Every web request starts with a handshake. Before any data moves, TCP makes the client and server agree they can talk. Here is the 3-way handshake in 4 tweets 🧵 (164 chars)

2/4 Step 1, SYN: the client says "I want to connect" and sends the sequence number it will start with. (102 chars)

3/4 Step 2, SYN + ACK: the server acknowledges the client's number and sends its own starting number back.

Step 3, ACK: the client acknowledges that. Now both sides know the other can send and receive. (202 chars)

4/4 Only after this does the actual data (your HTTP request) flow. My CN revision notes: https://github.com/minianon/1Shot-CN
