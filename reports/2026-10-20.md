Pattern of the week: Monotonic stack.

If a problem asks for the next greater, next smaller or "how many days until" something, stop and think stack.

How to spot it:
- For each element, you need the nearest element on one side that is bigger or smaller
- A brute-force nested loop keeps rescanning the same elements
- Histograms, temperatures, prices and spans show up a lot

The template:
1. Keep a stack of indices whose values stay in order (decreasing for next greater)
2. For each new element, pop while the top is smaller
3. Each popped element has just found its answer
4. Push the current index

Every index is pushed once and popped once, so O(n^2) becomes O(n).

Three problems to practise, in this order:
- Next Greater Element I
- Daily Temperatures
- Largest Rectangle in Histogram

Solve the first with the template above. The other two are the same idea with a twist on what you do when you pop.

Before you apply anywhere next week, fix these 6 things.

A recruiter opens your application, scans it for a few seconds, clicks a link or two and moves on. Most freshers lose at that stage, not at the interview.

Here is the checklist I would run:

1. Put everything behind one clear link. Resume in one place, projects in another and links buried somewhere is effort for the reader, and effort gets skipped.

2. Make the first screen answer one question: what can this person do? One line, then your two best projects.

3. Lead each project with what it does and who it is for. The tech stack comes second.

4. Tailor to the role. Reorder your projects so the most relevant one is first. Ten tailored applications usually beat fifty identical ones.

5. Send a short note with the application. Two or three lines: why this team, and one thing you built that relates to it.

6. Track what happens. Which applications got replies, which projects got opened? If you never look, you repeat the same mistake for months.

The last point is the one almost everyone skips. Without feedback you are guessing, and guessing feels like bad luck.

Then do the loop: change one thing, apply again, check again.

(114 chars) 1/5 One client hammering your API can slow it down for everyone. Rate limiting stops that. Explained in 5 tweets 🧵

(195 chars) 2/5 A rate limiter sits in front of your API and counts requests per client. Over the limit? It rejects with a 429 instead of letting the load through.

It also caps costs and softens some abuse.

(201 chars) 3/5 Token bucket: each request takes a token from a bucket that refills over time. No token, no request. Easy to allow short bursts.

Leaky bucket: requests queue up and are processed at a steady rate.

(154 chars) 4/5 Fixed window counts requests per time slice, but bursts at the boundary can slip through. Sliding window smooths that by weighing the previous window.

(232 chars) 5/5 With many nodes you need a shared counter, e.g. a central store like Redis, which adds latency and race conditions to handle.
