Pattern of the week: Binary search on the answer.

You do not need a sorted array to use binary search. You need a sorted yes/no question.

How to spot it:
- The problem asks for the minimum or maximum value that still works
- You can write a check: "does this value work?"
- If x works, everything bigger (or smaller) also works

Phrases like "minimum speed", "least capacity", "smallest largest sum" are the giveaway.

The template:
1. Pick a range [lo, hi] that surely contains the answer
2. Write feasible(mid) that returns True or False
3. If it works, keep it and search lower (hi = mid)
4. If it fails, search higher (lo = mid + 1)
5. When lo meets hi, that is your answer

Each check is O(n) and you do about log(range) of them, instead of trying every value.

Three problems to practise, in this order:
- Koko Eating Bananas
- Capacity To Ship Packages Within D Days
- Split Array Largest Sum

The hard part is never the loop. It is writing feasible() correctly.

In ShortlistMe, "publish" does not copy anything. It moves one pointer.

That one decision gave me version history and safe rollbacks almost for free. Here is the design.

The product: upload a PDF resume, AI turns it into a portfolio site. Users edit it, then publish it at their own URL.

The naive design: one portfolio row holding the current content. Every edit overwrites it. Publish just flips a flag.

The problem: an overwrite is permanent. One bad AI generation or a wrong edit and the old content is gone. And a published page changes the moment the draft does.

What I built instead (the schema is in the repo):
- Portfolio holds the slug and one nullable field, publishedVersionId
- PortfolioVersion is append-only, with a JSON data column and createdAt
- Every generate or major edit inserts a new version row
- The public page renders whichever version publishedVersionId points to

Publishing is two steps:
1. If the editor sent data, insert it as a new version
2. Update publishedVersionId to that version's id

Nothing is copied and nothing is overwritten. Pointing the page at an older version is the same update with a different id.

Trade-offs I accept:
- Storage grows with every edit. Portfolio JSON is small, so this is cheap, and old versions can be pruned later
- Reads need one extra lookup to follow the pointer
- The two steps are separate writes. A transaction would make them atomic, and that is the first thing I would tighten

The lesson: when users publish things people can see, separate "what exists" from "what is live". Make history append-only and make "live" a pointer.

4 things to check before you add a message queue:

- Does the caller really need the result right now?
- What happens when a message is processed twice?
- Where do failed messages go?
- Who watches the queue depth?

A queue moves the problem. It doesn't delete it.

1/4 A user taps "Pay", the network blinks, the app retries. Did you just charge them twice?

Idempotency keys are how APIs make retries safe. Explained in 4 tweets.

2/4 Idempotent means doing it twice has the same effect as doing it once.

GET and PUT usually are. A POST that creates a payment is not, unless you make it so.

3/4 The trick: the client generates a unique key per action and sends it in a header.

The server checks the key first. New key: run the logic and save the response under it. Seen key: skip the logic, return the saved response.

4/4 Details that matter: expire old keys, store the key in the same transaction as the write, and reject a reused key with a different body.
