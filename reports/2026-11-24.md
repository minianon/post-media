If a problem says "shortest path" or "minimum steps" on a grid, reach for BFS before anything fancy.

The signal:
- A grid or a graph where every move costs the same
- The question asks for the fewest steps, moves or minutes
- Some cells are walls, and you can move up, down, left, right

Why BFS works: it explores everything 1 step away, then everything 2 steps away. The first time you reach a cell is the shortest way to reach it.

The template in the image has three parts:
1. A queue that holds (row, col, distance)
2. A seen set, so no cell is queued twice
3. Four directions, with a bounds check and a wall check

Each cell enters the queue once, so the time is O(rows x cols).

Three problems to practise, in this order:
- Number of Islands
- Rotting Oranges
- Shortest Path in Binary Matrix

Rotting Oranges starts the queue with many cells at once. Once that clicks, a lot of grid problems get easier.

Every link in MiniLink gets a click counter. The interesting part is that a click is stored twice.

When someone taps a link, one API route does two writes:
- It creates a row in a Click table: link id, time, referer, country, city
- It increments a clicks counter on the Link row

Why both?

The Click table is the event log. Every click is kept, so I can answer new questions later: clicks per day, per country, per source. It has an index on (linkId, createdAt), so a time-range query on one link stays cheap.

The counter on Link is denormalized, and the comment in the code says so: it is there for performance. The dashboard shows total clicks on every link, and that should be a single read, not a COUNT over thousands of rows.

That is a classic trade: store the raw events as the source of truth, keep a cheap summary next to them for the hot read path.

There is one thing I would flag when reading my own code. The two writes are separate calls, not one transaction. If the second one fails, the log has a click the counter does not. For a link-in-bio page that is a fair trade, because the counter is a display number. For anything like billing, I would wrap both in a transaction, or derive the total from the events.

The lesson I take from it: decide which copy of the data is the truth, and decide what happens when the copies disagree.

Where do you keep a counter next to an event log, and how do you reconcile them?

#2 · 12:00 PM · Thread (4 tweets) · Thread · System Design · load balancing
🖼 https://raw.githubusercontent.com/minianon/post-media/main/2026/11-24/x-1200-1.png

1/4 Your app runs on one server. Traffic grows, and that one server is now your single point of failure.

The usual fix: run several servers and put a load balancer in front.

2/4 The load balancer gives users one public address. Behind it, it spreads requests across your servers.

Simplest strategy: round robin. Request 1 goes to server 1, request 2 to server 2, and so on in a loop.

3/4 It also runs health checks. If a server stops answering, the balancer stops sending it traffic until it recovers.

Users never notice one server dying. That's most of the value.

4/4 Catch: if the app keeps session data in a server's memory, a user bouncing between servers can get logged out. Store sessions in a shared place like Redis instead.

More concepts: https://github.com/minianon/System-Design

Round robin or least connections, which do you reach for?
