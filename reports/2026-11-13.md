1/4 A user taps "Pay". The network drops. The app retries.

Did you just charge them twice?

Not if the API is idempotent.

2/4 The client sends a unique Idempotency-Key with the request.

The API checks a key store first: have I seen this key before?

3/4 New key: run the payment once and save the response against the key.

Seen key: skip the work and return the saved response. Same answer, no second charge.

4/4 Detail that matters: store the key atomically with the write, and expire old keys on a schedule.

More concepts: https://github.com/minianon/System-Design

What else in your stack needs to be idempotent?
