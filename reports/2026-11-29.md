#2 · 12:00 PM · Thread · System Design · idempotency (5 tweets)
🖼 https://raw.githubusercontent.com/minianon/post-media/main/2026/11-29/x-1200-1.png

1/5 A user taps "Pay", the network drops, and the app retries. Did the money move once or twice?

This is the problem idempotency keys solve.

2/5 The client generates a unique key for the action and sends it with the request, e.g. an Idempotency-Key header.

The same action always carries the same key, even across retries.

3/5 The API checks a key store first: have I seen this key before?

New key: run the payment logic once, write to the database, save the response against the key.

4/5 Retry with the same key: the API skips the logic and returns the saved response.

Same answer, no second charge. Keys usually expire after a window, so the store doesn't grow forever.

5/5 Anything that writes money, orders or messages needs this. I keep a short note on it in my System Design repo: https://github.com/minianon/System-Design

Where have you seen a retry cause a duplicate?
