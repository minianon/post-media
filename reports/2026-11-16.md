You send 500 rupees to a friend. The database has to do two things: take 500 from your account, add 500 to theirs.

What if it crashes after the first step?

This is why transactions exist. A transaction groups steps so they behave as one unit. The classic way to remember the rules is ACID:

- Atomicity: all of it happens, or none of it. If the credit fails, the debit is undone (ROLLBACK).
- Consistency: the data follows its rules before and after, for example no negative balance if the schema forbids it.
- Isolation: two transactions running at the same time should not see each other's half-done work.
- Durability: once COMMIT returns, the change survives a crash or restart. Databases usually get this from a write-ahead log.

In interviews, "explain ACID" is rarely the whole question. The follow-up is usually "what happens if two transfers hit the same account together?" That is where isolation and locks (shared vs exclusive) come in.

1/4 Your app reads from one database. Traffic grows, and that same database now handles every read and every write.

One common fix: replicas. Here is how it works.

2/4 Primary-replica replication: all writes go to one primary.

The primary copies every change to one or more replicas. Reads can be spread across the replicas, so the primary has less to do.

3/4 The catch is replication lag.

A replica can be a little behind the primary. A user saves their profile, refreshes, and the read hits a replica that hasn't caught up. They see the old data.

4/4 A common fix: read a user's own recent writes from the primary, and send everything else to replicas. If the primary goes down, a replica can be promoted.

More in my System-Design notes: https://github.com/minianon/System-Design
