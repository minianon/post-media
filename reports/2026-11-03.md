Pattern of the week: Union-Find.

If a problem asks whether two things are connected, or how many groups exist, stop and think Union-Find.

How to spot it:
- Items that merge into groups over time
- "Are A and B connected?" or "How many components?"
- A cycle appears when you add an edge to an already connected pair

The template has two moves:
1. find(x): walk to the group's root, flattening the path as you go
2. union(a, b): join two roots, and report False if they already share one

With path compression, each operation is close to constant time, so you avoid rebuilding the graph with DFS each time.

Three problems to practise, in this order:
- Number of Provinces
- Redundant Connection
- Accounts Merge

Start with the first using only the template above. In the second, the False from union() is your answer. The third adds a mapping from emails to ids.

I set up my link preview wrong, and the fix took two commits.

I built AnonVault, a private workspace for project ideas, daily checklists and hackathon deadlines. When it was ready, I added Open Graph tags so a shared link would show a proper preview.

The mistake: I pointed og:image at a relative path, /favicon.svg. It looked fine in my head. The tag exists, the file exists, done.

What broke: link previews are fetched by someone else's crawler, not by my browser. A relative path means nothing to it. It needs a full URL.

Fix one, in my own commit history: switch to an absolute URL, https://vault.minianon.in/favicon.svg, and add og:url too.

That still was not enough for what I wanted. The next commit changed the image to favicon.png. Its message says it was to support WhatsApp link previews.

What I took from it:
- Treat the preview as an API for a stranger. Use absolute URLs, and a plain raster image.
- Test the share link where people actually share it. Opening the page in my browser proved nothing.
- Small bugs in the "boring" parts like meta tags are real bugs. They decide whether anyone clicks.

None of this is deep engineering, and that is the point. Some of my fix commits are about small details I assumed were fine.

1/4 Your page loads 50 posts. It feels slow, and the database CPU looks fine.

Often the culprit is the N+1 query problem. Here's what it looks like.  [149 chars]

2/4 You run 1 query to fetch the list of posts.

Then, in a loop, you run 1 more query per post to fetch its author.

50 posts = 51 round trips. Each one is cheap alone. Together they add up fast.  [196 chars]

3/4 The fix is usually one of these:

- JOIN the author in the first query
- Batch the lookups: WHERE id IN (...)
- With an ORM, use eager loading (include / select_related / preload)

Same data, one round trip.  [211 chars]

4/4 How to spot it: turn on query logging and open one page. If you see the same query shape repeated dozens of times, that's N+1.

Have you ever shipped one without noticing?  [175 chars]
