🖼 https://raw.githubusercontent.com/minianon/post-media/main/2026/11-17/linkedin-1.png

If a problem asks for the longest or shortest subarray or substring, try a sliding window first.

The signal: you are looking at a contiguous range, and you can tell whether a range is valid or not.

The idea:
- Keep two pointers, left and right.
- Move right to add a new element.
- While the window breaks the rule, move left to shrink it.
- Record the best window after each step.

Each element enters the window once and leaves once, so it runs in O(n) instead of the O(n^2) you get from checking every pair.

The template is in the image. The only thing that changes between problems is the rule that decides when the window is invalid.

Three problems to practise, in this order:
- Longest Substring Without Repeating Characters
- Minimum Size Subarray Sum
- Longest Repeating Character Replacement

A common slip: using an if instead of a while to shrink the window. One shrink step is often not enough.

A student's important information is scattered across WhatsApp forwards, PDFs, screenshots and notice boards. I built LifeOS to turn one upload into an action plan.

How it works:
- You drop in a screenshot, text or file.
- One orchestrator call (Groq) classifies the intent and returns which agents should run.
- Up to 7 agents run in parallel with Promise.allSettled: tasks, schedule, placement, reminders, expenses, study kits and drafts.
- If one agent fails, the others still return. One bad JSON response does not kill the whole result.

Two decisions I would keep:
- The orchestrator picks the agents, so an expense receipt never triggers placement logic.
- Guest mode. No login, data in localStorage, so anyone can try it in seconds.

One thing I should be upfront about: for the built-in demo examples, the API returns prestored answers after a fixed delay, to avoid hitting rate limits during live demos. Real input goes through the actual agents.

The bug that taught me the most was stale guest data. Guest results live in localStorage, so after a deploy, returning visitors could still be carrying data from an older version. The fix was two small things: a version guard that clears the guest keys when the app version changes, and making guest mode start fresh on every visit. I also bumped the service worker cache name so old cached assets would not linger.

The lesson: anything you persist on the client needs a version, or your next deploy will meet last month's data.

The bigger lesson: multi-agent sounds impressive, but the useful parts are routing and failure handling, not the number of agents.

Try it: https://lifeos.minianon.in

1/5 A user uploads a resume. Your API parses it, calls an AI model, saves the result, then replies.

That's 20 seconds of a spinner.

A message queue fixes this. Here's the idea:

2/5 The API does only the quick part: it puts a job in a queue and replies "accepted" right away.

The user isn't stuck waiting for the slow work.

3/5 A consumer picks jobs off the queue and does the slow work in the background.

Traffic spike? Jobs wait in line instead of crashing the app. Add more consumers to catch up.

4/5 Queues also decouple your services. If the consumer goes down, the jobs stay in the queue, so nothing is lost while it restarts.

5/5 Jobs that keep failing go to a dead-letter queue, so one bad message doesn't block the rest.

More in my System-Design notes: https://github.com/minianon/System-Design
