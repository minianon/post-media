Most freshers send 40 applications and hope.

A few send 10 that were actually prepared. In my experience, the second group gets more replies.

Here is the routine I would follow before sending anything:

- Read the role twice and match it to skills you really have
- Pick one relevant project, not all eight
- Write a 3-line message: who you are, why this role, one proof
- Link one working demo that opens fast
- Follow up once after a week, politely

Recruiters skim. They are not checking how much you did. They are checking whether you did the right thing for this role.

One focused application shows that you read the job post. A copy-paste one shows that you did not.

Quantity feels productive, but preparation is what gets the reply.

1/5 Your API is public. One buggy client retries in a tight loop and sends 10,000 requests a minute.

Everyone else gets slow responses. How do you stop that?

A rate limiter.

2/5 It sits in front of your API servers. Every request is checked against a limit per user, API key or IP before it gets through.

3/5 Token bucket: a bucket refills at a steady rate. Each request takes a token. Empty bucket means rejected. It allows short bursts but keeps the average rate fixed.

4/5 Over the limit? Return 429 Too Many Requests. With several API servers, the counters must live in a shared store (like Redis), or each server counts separately.

5/5 More concepts like this are in my System Design notes: https://github.com/minianon/System-Design
