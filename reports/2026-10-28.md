A security rule that blocked the whole internet.

I was building a gateway that lets an admin add MCP servers by URL. Because the server fetches URLs for you, it needs an SSRF guard: reject anything that resolves to a private, loopback or cloud-metadata address.

It looked fine until I tried adding a real public server. Every request was blocked.

The cause was one line:

- I had a rule to block IPv4-mapped IPv6 addresses (::ffff:0:0/96).
- Node's BlockList treats a mapped address and the plain IPv4 address as the same thing.
- So that single rule matched every IPv4 address, including 8.8.8.8.

The fix was to delete the rule. Mapped addresses are already matched by the IPv4 rules. Then I added a regression test that checks public addresses are allowed, not just that private ones are blocked.

Lessons:
- Test the allow path of a deny-list, not only the deny path.
- Run security code against real traffic early. A real public URL found what my first tests missed.
- A library that normalises input for you can quietly change what your rule means.

Code: https://github.com/minianon/urumi-mcp-gateway

1/4 Rolling update on Kubernetes, and a few requests still fail. Why? The pod gets SIGTERM while the Service is still sending it traffic. Here's the fix, in 4 tweets 🧵

2/4 Problem: removing a pod from the endpoints and sending SIGTERM happen at the same time. For a moment, traffic still arrives at a pod that is shutting down.

3/4 Fix part 1: a preStop sleep (5s) so routing catches up. Part 2: on SIGTERM, flip /readyz to 503, finish in-flight requests, then exit, with a hard timeout as a safety net.

4/4 In my gateway, a rollback under load lost 6 of 528 calls before this and 0 of 525 after. Code: https://github.com/minianon/urumi-mcp-gateway
