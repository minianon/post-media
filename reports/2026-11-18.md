I built an AI agent to research 100 apps. Checking its work turned out to be the real project.

Buildability is a case study where an agent researches 100 apps for agent-toolkit buildability: auth method, self-serve or gated access, API surface, official MCP, and a green/yellow/red verdict with evidence links.

The engineering lesson was verification, not the agent.

- Every app goes through one shared schema and rubric, so 100 runs stay comparable
- A second pass is told to refute the first one, not agree with it
- I spot-checked a sample of 16 against the live official docs

What the check found: 9 confirmed, 1 partially wrong, 1 clearly wrong (a free sandbox mislabelled as a trial). 5 docs were unreachable, so I marked them UNVERIFIABLE instead of counting them as hits.

On the conclusive checks, accuracy went from 82% to 100% after the fixes.

The agent fleet also kept hitting a session limit, so the research step only picks up apps that don't have a record yet. A rerun just fills the gaps.

Lesson: an unverifiable claim is not a correct claim. Say so on the page.

How do you check AI output before you trust it?

#2 · 12:00 PM · Thread (5 tweets) · Thread · System Design · consistent hashing
🖼 https://raw.githubusercontent.com/minianon/post-media/main/2026/11-18/x-1200-1.png

1/5 You have 4 cache servers and route each key with hash(key) % 4.

Now add a 5th server. Almost every key maps somewhere new, so your cache goes cold all at once.

Consistent hashing fixes this.

2/5 Hash the servers onto a ring of positions. Then hash each key onto the same ring.

The ring is just a circle of hash values, nothing fancy.

3/5 A key is served by the first server clockwise from its position.

Add a server and it only takes keys between itself and the previous server. Remove one and only its keys move to the next.

4/5 On average only about K/N keys move (K keys, N servers), instead of nearly all of them.

Catch: servers can land unevenly on the ring. The usual fix is virtual nodes, many ring positions per server.

5/5 More concepts like this in my System Design notes: https://github.com/minianon/System-Design

Where have you seen it used: caches, DB sharding or load balancers?

Weaave runs a workflow as a graph of Promises.

The old version went layer by layer, so one slow node blocked unrelated branches.

Now each node awaits only its own parents. Independent branches run freely, and a failure only stops its own branch.
