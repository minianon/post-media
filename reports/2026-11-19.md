Should I learn a new stack before I apply?

Freshers ask me this all the time, usually after seeing a job post that lists a different framework.

My answer: go deep first, then extend.

Why it works:
- Interviews test fundamentals: data structures, HTTP, databases, concurrency. These carry over between stacks.
- One shipped project in one stack proves more than five tutorials in five stacks.
- A second stack takes weeks, not months, once the first one is solid.

I have seen this in my own path. I have built projects in TypeScript and Next.js, written Python for trading infrastructure, and worked in Go during my Microsoft internship. Each switch got easier because the concepts were the same: APIs, queues, caching, failure handling. Only the syntax changed.

A simple rule:
- Pick the stack your best project already uses.
- Make it production-like: auth, a database, a live link.
- Then learn a second stack by rebuilding one small piece in it.

Switch earlier only if the roles you actually want ask for something else. Switch with a purpose, not out of fear.

1/4 Your app loads the same few user profiles from the database again and again.

Every request pays for a query whose answer barely changed.

The simplest fix has a name: cache-aside.

2/4 How it works:

1. App checks the cache first
2. Hit: return it, done
3. Miss: read from the database
4. Store the result in the cache with a TTL

The cache only ever holds what was actually asked for.

3/4 The TTL is your trade-off. Short means fresher data but more database reads. Long means fewer reads but staler data.

On writes, update the database, then delete the cached key. The next read refills it with fresh data.

4/4 One more thing to watch: when a hot key expires, many requests can miss at once and all hit the database together.

More caching and system design notes: https://github.com/minianon/System-Design

Which one has bitten you: stale data or a burst of misses?
